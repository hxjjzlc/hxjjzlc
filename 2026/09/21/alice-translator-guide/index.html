爱丽丝语翻译器：无后端实现与 API 调用指南

发表于2026-09-21|更新于2026-09-21
|浏览量:|评论数:

在线地址：**https://hxjj.dpdns.org/alice/**
用于对照的老后端：http://localhost:5196（仅本机）

把一段正常文字按 UTF-8 编码成字节流，再强行用 Shift-JIS（cp932）去解码 —— 得到的那串伪日语乱码，就是「爱丽丝语」。反方向再来一次，就能还原。

原先这套东西跑在一个 Python 后端上。现在它变成了一张纯静态网页：零服务器、零依赖、零网络请求，双击 HTML 就能用；而且它依然可以被程序调用，有四种调用方式，下面会全部写清楚。

一、先看效果

正常文字 爱丽丝语 能否完美还原
世界 荳也阜 ✅
爱丽丝语 辷ｱ荳ｽ荳晁ｯｭ ✅
爱丽丝语翻译器 辷ｱ荳ｽ荳晁ｯｭ鄙ｻ隸大勣 ✅
こんにちは世界 縺薙ｓ縺ｫ縺｡縺ｯ荳也阜 ✅
Hello, World! Hello, World!（英文原样不动） ✅
中文测试 荳ｭ譁�豬玖ｯ� ❌ 丢了 2 个字符

二、网页怎么用

打开 https://hxjj.dpdns.org/alice/，左边是正常文字，右边是爱丽丝语：

  • 翻译成爱丽丝语 → 把左边的内容编码成乱码；
  • ← 译回正常 把右边的乱码还原回正常文字；
  • 中间的 ⇄ 直接交换两侧内容；
  • 每侧都有「复制」按钮，右侧还有「清空」。

页面上那行状态提示会告诉你这次转换有没有丢失字符，丢了多少。往下展开「原理详解与字节级追踪」，还能看到 UTF-8 的每一个字节是怎么被 cp932 一步步读掉的 —— 教学意义大于实用意义，但很直观。

三、原理：同一串字节，两套码表

方向 第一步 第二步 结果
正常 → 爱丽丝语 UTF-8 编码 cp932 解码 世界 → 荳也阜
爱丽丝语 → 正常 cp932 编码 UTF-8 解码 荳也阜 → 世界

以 世界 为例：它的 UTF-8 字节是 E4 B8 96 E7 95 8C，共 6 个字节。而 cp932 是双字节编码，于是这 6 个字节被两两成对地读成三个字符：E4B8→荳、96E7→也、958C→阜。就这样变成了三字日语乱码。

为什么会有损

并不是所有字节组合都能在 cp932 里找到对应字符。找不到的字节会被替换成 U+FFFD（就是那个 �），这部分信息在还原时永久丢失，找不回来。

中文比较容易被切到这种边界上，日文和英文则基本能完美往返 —— 因为日文的 UTF-8 字节序列恰好大多能落在 cp932 的合法双字节范围内。

为什么可以不要后端

这里有个坑：浏览器自带的 shift_jis 解码器，和 Python 的 cp932 并不是同一个东西。至少有两处不一样：

差异点 Python cp932 浏览器 shift_jis
单字节 A0 / FD / FE / FF 映射到私有区 U+F8F0~`F8F3` 判为非法 → �
前导字节 + 未定义尾随字节（如 87 E6） 只消耗前导 1 个字节，继续往下读 吃掉 2 个字节，一起报废

用一个词就能测出来：你好。它的 UTF-8 字节里含一个 A0，Python 会把 A0 单独解成 U+F8F0（一个不可见的私有区字符，夹在 菴 和 螂ｽ 之间），浏览器原生解码器却会输出 � —— 同一串字节，两种结果。用日文或英文测试是发现不了的，只有中文会踩到。

所以这张页面内嵌了一份由 Python 生成、逐项校验过的 cp932 码表（60 个前导字节 × 188 个尾随字节 = 11280 项），并在浏览器里按 Python 的规则手写了解码器。反向编码不额外存表，直接由正向表反查构建（cp932 有 6 处非对称映射，这几条单独补上）。

结果就是：这张静态页面与你本机的 Python 后端逐字节等价，两边可以互相接续翻译。详见第五节。

四、无后端也能有 API

静态站点没有任何进程来返回 HTTP 响应，所以「命令行 curl 直接调」这种事是做不到的。但在浏览器里被程序调用完全没问题 —— 因为算法本来就全在浏览器里。下面四种方式按「谁在调用」挑一种就行。

① 同源页面调用：当 JS 模块用

在自己的页面里引一下库，就有一个全局对象 AliceTranslate：

可用的方法：

方法 返回
AliceTranslate.to(text) 爱丽丝语字符串
AliceTranslate.from(text) 正常文字字符串
AliceTranslate.toAlice(text) 完整结果对象
AliceTranslate.fromAlice(text) 完整结果对象
AliceTranslate.translate(text, mode) 完整结果对象，mode 取 to / from
AliceTranslate.version 版本号

mode 除了 to / from，还接受 decode、back、reverse 这几个别名；传了不认识的值会按 to 处理。

② 跨站调用：脚本标签 / JSONP 端点

alice-core.js 同时也是一个端点。只要在 URL 上带参数，它加载时就会顺手算完并回调 —— 浏览器对 <script src> 不做同源限制，所以任何站点都能用，不需要对方配 CORS：

支持的参数：

参数 说明
text / q / t 要翻译的文字（建议 encodeURIComponent）
mode to（默认）/ from
callback / cb 回调函数名，支持 a.b.c 这种路径写法
target 把结果直接写进页面里某个元素的 value 或 textContent（传元素 id）

几点说明：

  • 回调是通过沿路径解析真实函数来调用的，没有用 eval；回调名还会先做合法性校验（alert(1) 这类会被拒绝）；
  • 如果不想用回调，也可以在页面里监听事件：window.addEventListener("alice-api", e => console.log(e.detail))；结果同时也会放在 window.ALICE_API_LAST；
  • 不带任何查询参数时，这个文件就是普通库，不产生任何副作用，不会发请求、不会写全局变量以外的东西。

③ 同源 fetch / JSON：真正的 HTTP 接口

这一条最像「正常的 API」。页面会注册一个 Service Worker，它只接管一个路径：/alice/api，并在浏览器内部直接返回 JSON：

长文本用 POST，避免 URL 长度限制：

不带 text 直接 GET /alice/api，会返回一份接口自描述（版本、端点列表、示例）。另外 &pretty=0 可以关掉 JSON 缩进。

页面上还放了一个现场自测按钮（「无后端 API」区块里的 ⑤），点一下就会真的发一个 fetch("/alice/api?text=…") 并把返回的 JSON 原样贴出来 —— 怀疑它在不在工作时，点它最快。

④ 页面深链：把结果做成一串网址

就是第二节里那种 ?text=…&mode=…。适合分享，也适合塞进 <iframe>。

接口返回格式

四种方式返回的数据结构是统一的：

  • mode：to = 正常 → 爱丽丝语，from = 爱丽丝语 → 正常；
  • lost：无法映射、永久丢失的字符数；
  • lossless：就是 lost === 0。

失败时返回 {"ok": false, "error": "…"}，HTTP 状态码会给 400（请求格式不对）或 405（方法不支持）。

能力边界

能力 本页（无后端） Python 后端
浏览器里调用 ✅ 模块 / JSONP / fetch ✅ 需处理跨域
跨站调用 ✅ 脚本标签（JSONP） ⚠️ 要自己开 CORS
命令行 curl ❌ 没有服务器进程可访问 ✅
非浏览器客户端、机器人 ❌ ✅
要装的东西 无，一张静态页 Python + 常驻进程

一句话：网页内能做的调用，无后端全都能做；网页外（curl、机器人、别的语言的程序）的调用，才必须要有后端。 因为静态站点没有任何东西能在 HTTP 层返回自定义响应头与 text/plain —— 本页的 /alice/api 是 Service Worker 在浏览器内部拦下来的，所以它只对装过这段脚本的浏览器有效，而且同一个源才行。

五、和 Python 后端的关系

新旧两版是逐字节等价的：同一段文字，无论走静态页还是走 localhost:5196，结果完全一样，可以一边翻译、另一边还原。

为了确认这一点，我把内置实现和真实后端（直接 import server.py，不走网络）做了三轮对照，全部零差异：

对照项 规模 结果
翻译结果（to_alice / from_alice / lost） 3086 组用例 0 处不一致
UTF-8 编码（含孤立代理项） 3086 组 0 处不一致
反向编码表全量 9408 条 0 处不一致

用例里包含 U+0000~`U+00FF` 全覆盖、半角片假名、全角区、全部 2048 个代理项单点、随机字节流、增补平面字符（emoji）以及最长 3000 字的长文本。

对照过程中抓到两个隐藏问题，都已修掉：

  1. 反向还原时按 UTF-16 码元遍历，导致 emoji 这类增补平面字符被拆成两个代理项、多算一次丢失。Python 的 for ch in text 是按码位遍历的，改成按码位遍历后一致。
  2. 孤立代理项：Python 用的是 errors="surrogatepass"，会把孤立代理项按它自己的码位编成 3 个字节；而浏览器原生 TextEncoder 会把它替换成 U+FFFD。这个差异只在不正常构造的字符串上出现，但既然要「逐字节等价」，就补了一个等价实现（正常文本仍走原生快速路径，没有性能代价）。

六、注意事项

  • 有损是特性不是 bug。翻译阶段丢掉的字符永远回不来，这是 cp932 装不下所有 UTF-8 字节序列的必然结果。
  • 深链受 URL 长度限制，很长的文本请用 POST /alice/api 或直接粘贴。
  • /alice/api 需要 HTTPS（或 localhost），且本页被访问过一次之后 Service Worker 才会激活。在 file:// 下打开时，① ② 两种方式照常可用，③ 不可用。
  • Service Worker 只接管 /alice/api 这一个路径，其它请求一律放行，对站点其它页面没有影响。想卸载：开发者工具 → Application → Service Workers → Unregister。
  • 所有计算都在你自己的浏览器里完成，文字不会被发送到任何地方 —— 这一页根本没有任何后端可以发送。

七、想自己重建

页面的三个产物是这样来的：

文件 说明
index.html 界面 + 内嵌码表 + 算法 + API 层，自包含，可离线
alice-core.js 可复用库，同时兼作 JSONP 端点
sw.js Service Worker，提供 /alice/api

构建与验证脚本都在 E:\workspace\skill\workbuddy\alice-translator-api\scripts\：gen_code_table.py 从 Python 的 cp932 编解码器导出码表；build_frontend_page.py 一键生成三个产物；gen_testcases.py + verify_against_backend.js 做上面那三轮对照。改完算法跑一遍构建脚本，产物会自动同步到站点源目录，然后正常部署即可。

爱丽丝语的有趣之处恰恰在于它的不完美：能完美往返的句子像暗号，丢过字的地方则永远回不到原来的样子。
