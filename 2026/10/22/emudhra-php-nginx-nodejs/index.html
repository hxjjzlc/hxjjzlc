四天之内三连爆：eMudhra 中间证书私钥可被推算，以及同期爆发的 PHP、nginx、Node.js 漏洞

发表于2026-10-22|更新于2026-10-24
|浏览量:|评论数:

2026 年 10 月 17 日到 21 日，安全圈在四天里被塞了三件事：

  1. 印度 CA eMudhra 的 8 张中间证书，私钥根本不用”偷”——从公开证书里就能算出来；
  2. PHP 爆出两个 CVSS 4.0 满分 9.2 的未认证 RCE（php2shell），已在野利用；
  3. nginx 和 Node.js 紧接着发安全版本，各带一堆内存破坏 / TLS 校验绕过。

我做了个纯前端检测页，直接在浏览器里测”你这台设备现在还信不信那批问题证书”：

https://hxjj.dpdns.org/emudhra-cert-check/

打开点一下就行，不上传任何数据。下面把三件事拆开讲。

一、那个检测页到底在测什么

判定原理只有一条：图片能不能加载

页面里没有任何 fetch / XMLHttpRequest / WebCrypto，只用了 new Image()：

为什么用 <img> 而不是 fetch：跨域 fetch 会被 CORS 挡在”拿到响应”之前，而且拿不到”TLS 握手是否成功”这个信息；<img> 只要 TLS 握手过了 + 资源是图片，就触发 onload，是纯前端唯一能探到”证书被不被接受”的手段。

关键点在于反直觉的配色：

结果 含义 颜色
加载成功 当前客户端接受了问题证书链 → 有风险 红
加载失败 已拒绝，或网络不可达 / 404 绿
超时 结果未知，既不算信任也不能算安全 黄

所以”图片加载成功”反而是坏消息。我第一版做的时候下意识把成功涂绿，看了两秒才意识到全反了。

8 台端点 = 同一批证书的 8 种链构造

它们全是 dv-g3b 这一族，后缀区分的是链怎么搭：是否经 AAA Certificate Services 交叉签名（-aaa），服务端证书 / 中间证书走 RSA 还是 EC（-rsa / -ec），以及组合。

为什么要拆这么细：同一个信任库对这批证书的封锁可能是有缺口的。比如某个客户端只删掉了 emSign ECC Root CA - G3 而留着 AAA Certificate Services，那”直连 emSign”那条链会被拒，但”经 AAA 交叉签名”那条链照样能建起来——结果就是同一批被吊销的中间证书，一半被拦、一半被放行。所以只测一台主机得出的”安全”结论并不可靠。

官方站点给的是 12 台（dv/ov/ev × g3b/g3c × 直连/AAA）。我这个页面用的是 dv-g3b 的 8 种变体切片，测的是同一批证书，切片角度不同。

这个页面测不到什么

诚实说明，别把它当安全认证：

  • 测不到证书链本身。纯前端读不到链、读不到系统证书库，只能得到”加载成功 / 失败”这一个布尔值。
  • “失败”≠ 安全。可能证书被拒，也可能 DNS 挂了、返回 404。页面把这事写在说明里了。
  • 只代表当前浏览器 / WebView。鸿蒙原生应用走 @ohos.net.http，用的是系统证书库，和浏览器不是一条路。
  • 不看 UA、不看系统版本，结论完全由 8 个端点的实测结果汇总得出——环境信息只是打印出来给人看的，不参与判定。

顺带一个实现细节：每个端点独立 Image、独立 6 秒超时、独立 done 标记。finish() 第一行就是 if (ep.done) return;，否则 onload 和 setTimeout 抢跑会让同一个端点被计两次，汇总数字就废了。

二、eMudhra：私钥不是被偷的，是被”写错”的

这是整件事最离谱的地方：没有入侵，没有窃取，是 CA 自己把私钥生成坏了。

P-384 的私钥本应是一个 384 位随机数（大约 10¹¹⁵ 种可能）。eMudhra 在 2025 年 4 月 30 日的一次密钥生成仪式上，把 8 张中间 CA 的私钥生成成了极小的整数。研究者和 Mozilla 独立还原出来的值是：

全部小于 256。也就是说，任何人拿公开证书 + 几百次椭圆曲线点加，就能反推出私钥——毫秒级。这不是”密码学被攻破”，这是”保险箱密码刻在箱门上”。

唯一的幸运：CT 救了浏览器

这 8 张中间证书从来没进过证书透明度（CT）日志。Firefox / Chrome / Edge / Safari 都强制 CT，所以它们根本不可能被这种手法攻击——攻击者没法偷偷签发一张能过 CT 校验的证书。代价是反过来的：正因为没进 CT，也就没有”事后追查签发记录”的线索。至于不强制 CT 的客户端（命令行工具、服务端库、嵌入式设备），报告的原话是：没人知道有没有被利用过。

真正的坑在浏览器之外

浏览器靠 OneCRL / CRLite / CRLSets 这些带外通道下发封锁，用户什么都不用做。但很多软件自带证书包、且从不查吊销，CA 的吊销对它们等于不存在——只有升级软件才能解除信任。

这就是为什么”浏览器早就没事了”和”你服务器可能还有事”能同时成立。最典型的是 Java：默认读 $JAVA_HOME/lib/security/cacerts，com.sun.net.ssl.checkRevocation 默认 false，还不强制 CT。实测 Liberica JDK 21.0.10 对 12 台测试主机全部握手成功。临时缓解是把根从 keystore 里删掉：

macOS 也有个坑：系统层面确实拦了，但 /usr/bin/curl 是对着 /etc/ssl/cert.pem 校验证书的、完全不查吊销，而这个文件没跟着更新。于是 Safari 拒绝、终端里的 curl 照收。

三、PHP：php2shell，两个 9.2

10 月 21 日，PHP 发了紧急安全版本，修两个未认证远程代码执行：

CVE 机制 严重性
CVE-2026-109618 OOM 处理在内部请求数据只初始化了一半时打断 PHP，请求清理阶段把非法数据当成合法的用 CVSS 4.0 9.2
CVE-2026-109619 请求私有状态在其底层内存释放后仍然存活，同一 worker 处理的下一个请求在正常初始化重置它之前就用了这份残留 CVSS 4.0 9.2

修复版本：

几件事值得单独记一下：

  • 影响面是”所有对外提供 HTTP 的 PHP”：PHP-FPM、Apache + mod_php、php-cgi、FrankenPHP、LiteSpeed 全线。官方认为 mod_php 风险最高——已有利用能证明单个未认证请求在任何应用代码执行之前就打进去。
  • 已经在野利用了。Wiz 的评价是这两个洞”存在了几十年”，只是利用链复杂到接近人类研究者的极限；前沿 AI 模型把这道门槛降下来了，于是几十年老洞变成了可用 exploit。
  • 没有完整缓解措施，升级是唯一解。PHP 8.1 及更早已停止支持，但安全团队仍给 7.4 / 8.0 / 8.1 出了最小源码 backport。靠 rpms.remirepo.net 的要注意：当天那个仓库不会有更新，得换发行版包或自己编。
  • Cloudflare 已经给已知利用路径上了 WAF 规则，免费套餐也有——但这只是兜底，不是修好。

四、nginx：三个 9.2，全是内存破坏

F5 在 10 月 14 日一次性发了 5 个公告，其中 3 个内存破坏在 CVSS 4.0 下都是 9.2（CVSS 3.1 是 8.1），nginx 项目自己标 medium——评分口径差得挺远。

CVE 类型 触发条件
CVE-2026-97205 use-after-free（ngx_http_core_module） 开了异步文件 I/O（AIO）+ 处理含 include virtual 的 SSI 页面
CVE-2026-93479 堆溢出 map 用了正则匹配，而 root 或 access log 格式先引用了 map 的正则捕获变量、后引用 map 输出变量；或字符串表达式里用了不可缓存变量
CVE-2026-15176 堆溢出（ngx_http_core_module） location 里 alias + rewrite + 引用 $request_filename；或 log_format 里用了 $request_filename
CVE-2026-97629 TLS 会话伪造（8.3） 共享 SSL session cache 但没显式配 session-ticket key → 可能绕过客户端证书校验
CVE-2026-95101 HTTP/3 请求体注入（6.9） 开了 HTTP/3 + proxy_request_buffering，可往转发给后端的请求里塞数据

三个内存破坏的共性：未认证远程一个构造请求就能打，但都要求特定配置；代码执行需要 ASLR 被关闭或被绕过，所以 F5 的措辞是”可能执行代码”而不是”必然 getshell”。

修复：

改不了的临时招：CVE-2026-97205 关掉 AIO 或 SSI（二选一，关 AIO 会影响大文件/流媒体的吞吐）；CVE-2026-93479 把无名正则捕获换成命名捕获，并且只在匹配块内部用；CVE-2026-15176 避开 location 里的 alias 和 $request_filename。

改配置前先 nginx -T 把实际生效的配置 dump 出来对一遍——你以为是默认的，往往早就被某个人改过了。

同样是 10 月 21 日，Node.js 发了 22.23.4 / 24.22.1 / 26.12.1，10 个漏洞（4 high / 3 medium / 3 low）：

CVE 级别 问题
CVE-2026-111497 high Brotli 解码器越界写 → 可 RCE。处理不可信 Brotli 压缩数据的服务重点看
CVE-2026-105482 high dns.resolve 遇到含 NUL 字符的域名会截断
CVE-2026-105483 high 用全角数字写 IP 时绕过 TLS 证书主机名校验（26.x / 24.x）
CVE-2026-106069 high 主机名”松散解析”成 IP 时绕过 TLS 主机名校验（全分支）
CVE-2026-105481 medium keep-alive socket 会处理在请求发出之前就已写好的响应
CVE-2026-106072 medium 非规范 IPv4 主机名校验不当，DNS SAN 能冒充 IP 端点
CVE-2026-106074 medium randomUUID() / randomInt() 的熵缓存被写进启动快照和 SEA → 每个进程重复同一批值
CVE-2026-106070/106071/106073 low ZIP 头校验失败后返回攻击者可控前缀；Permission Model 通配符越权、fs.realpathSync 绕过

这次发布同时更新了内置 CA 证书包（就是上面 eMudhra 那件事的收尾），另外还带了 c-ares、OpenSSL（24.x / 22.x）、SQLite（22.x）、Undici 的依赖更新。

两个提醒：

  • 打包成单可执行文件（SEA）或用启动快照的，升级完要重新构建——CVE-2026-106074 那个熵缓存就藏在快照里。
  • EOL 分支同样受影响，但不会有补丁。生产环境锁在旧版本上的，这次必须动。

六、三件事为什么会挤在一起

表面上”四天三爆”，其实是三条互不相干的战线刚好撞在同一周，但它们的共同点很值得记：

  1. 信任根是最脆的一层。eMudhra 这件事不需要任何 0day，只需要一个错误的密钥生成仪式——一次人为失误污染了整个 PKI 的信任基础。浏览器 3 小时就封住了，而服务器、容器、嵌入式设备可能要几个月。
  2. “补丁”和”生效”是两件事。同一个二进制，浏览器里拒了、命令行里收；同一个主机，curl 拒了、Node 收。判断有没有中招只能实测，不能看版本号猜。
  3. 运行时层正在被集中打。PHP 那两个洞存在了几十年，是 AI 把利用链的门槛压下来之后才被真正打通的；nginx 和 Node.js 全是内存安全问题。”升级运行时”这件事的优先级，这一年明显该往上提。
